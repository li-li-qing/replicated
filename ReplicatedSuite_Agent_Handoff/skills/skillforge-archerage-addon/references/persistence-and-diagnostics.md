# 存档格式、回读与恢复

遇到 `fingerprint_mismatch`、批量导入无效、重载丢设置时先读本页；报告如何完整交付见[诊断报告工作流](diagnostic-report-workflow.md)。本页提炼的是保存边界，不是任意 Hash 修复器。

## 1. 把故障放回实际阶段

分别记录 **业务 schema、codec、transport、integrity、envelope、owner/scope、加载 generation**。当前代码能写新格式，不表示磁盘旧档已转换；同一构建标签也不保证源码相同。

```text
用户命令 → 待提交业务值 → canonical/编码 → Native 保存
         → Native 回读 → transport 解码 → codec/canonical 校验
         → 提交内存状态 → 下一次插件加载读取
```

`pcall=true`、API逻辑成功、数据回读成功、耐久验证成功、重载保留是不同结论。`PERSISTENCE_FAILURES failed=0` 可能只统计加载失败，不能反证 `durableFail=1` 或 `readbackVerifyFail=1`。统计阶段、错误历史和当前保护状态须分别解释。

优先打印首个结构差异的路径、两侧类型、受限值摘要、输入/输出数量，而不只打印两个 Hash。例如 `tracked.auto.189: number vs nil` 的 **189 是数组位置，不是 Buff ID**。它确认了回读表示少项，还不能单独确认是 Native 落盘、LoadData 返回还是解码/规范化先丢掉该项。

## 2. 声明值与实际值必须绑定

对当前 canonical 指纹分支，令 S 为载荷声明值，E 为本次预期指纹，A 为回读业务值重算指纹：应验证 **S == E == A**，还要通过身份、envelope、解码和容量检查。只验证 E == A 可能把下次加载会拒绝的存档当成保存成功。

旧版指纹可能针对编码载荷，不能跨格式直接比较。经明确许可的表示恢复分支应记录输入、算法和理由，再比较同语义指纹。不要为了通过检查重盖 S、跳过校验、排除差异字段或把整个文件迁移成默认配置。

必须覆盖合法 `false`、`0`、空串、空表、保留前缀字符串、数字/字符串键碰撞、稀疏数组、数值精度和循环引用。Lua 中0和空串本身为真，不能把所有问题都归因于 `or`。

## 3. 数值表示：恢复证明不等于找回原值

先按故障文件版本验证旧 canonical，再执行业务迁移；先套新版默认项再验旧章可能制造假故障。核对：有效数字与固定小数、binary32转换顺序、整数/非整数格式分支、指数正负号和宽度、时间单位、平台格式化差异。

Replicated Suite 的历史样本曾支持两类模型：窗口比例跨越旧六位有效数字边界；时间值经精度转换变为整数，旧格式选择了另一条指纹分支。它们是指定样本的可复现解释，**不是所有 RU 数字都会如此的证明**；其他 Store、字段和客户端不能直接套用。

受限恢复须同时具备：明确版本/owner/字段范围、可信输入形状、有限候选集、可解释损失模型、唯一整份旧指纹匹配、拒绝反例。已有一致性 Hash 不是密码学认证；不能任意枚举业务值直到碰撞。`tries=0` 应解释为没有执行候选验证，`hits=0` 不证明尝试穷尽；字段 nil 只说明该恢复路径没有输入。诊断 `tested` 必须与真实执行计数一致。

候选可仅作为历史指纹的见证；实际业务值仍保留原始读出值的分支，应明确记录，不能把见证小数描述为找回的准确原值。加载恢复、后续重新盖章保存和新传输格式是三个独立动作。

## 4. 批量 ID 与物理传输预算

一键导入的成功条件是 **计划集合 → 全量保存 → 全量回读校验 → UI展示已提交集合 → 重载保留**。把列表切换到“已追踪”只能改善展示，不能修复回读少项。

本轮材料中，“推荐397项、第189项起缺失”的模拟复现了用户报告差异。该数字是案例条件，不能把188写成所有Native表的硬上限。回归应在多个截断点、不同字符串长度、键类型和节点预算下验证，而不只用无限制深复制替身。

当真实边界无法保全长数字数组，可按 **指定 Store、显式版本** 编码为有界短字符串块。物理格式必须描述总数、块序号和校验；解码拒绝缺块、重复索引、乱序歧义、非法ID、未知标签、错误数量/校验和额外包装字段。业务仍得到完整逻辑集合，不降低追踪上限，不把尾部丢失当正常。

每块字节、块数、总节点、深度和总载荷均需预算；压缩不能保证任意数据都装得下。分块不能变成多次无事务保存后谎称原子提交。数字保护、转义和旧解码路径不得被新序列编码覆盖。

在本次源码快照中，状态显示单独启用 Transport4，其余Store默认Transport3。未来任务读取注册处核对，**不把“都改T4”写成固定要求**。新物理格式需保留旧读、明确回退要求，并验证保存与重载。

## 5. 回滚与只读取证

内存事务回滚不意味着Native已写的数据也回滚。回读失败后的UI恢复旧集合，磁盘仍可能是不完整新载荷；直接重载可能把它变成加载失败。报告必须分开 pending、committed memory、physical readback、write fence。

不应通用建议“保存默认值/退出游戏/反复重载就好”。若现有已验证旧快照仍在内存，可先评估项目已有的可靠恢复写入路径；它是写操作，须有明确依据和风险说明。否则先保留原档并只读取证。

原档读取不得执行默认化、迁移、应用、保存或清错。Native返回表不是物理磁盘字节。授权分析UDF时在只读副本核对格式、活文件集合、序号和删除标记，不能把旧版本/失效记录冒充当前配置；数据库读取权限和文件格式未确定时不猜解析。采集其他插件或账号资料前说明范围，交付包不夹带这些数据。

## 6. 必测与拒绝条件

旧格式正常读取；合法空值；数字与键的往返；397项一类大集合与最大边界；错误声明S；错误内容A；缺块/超预算；保存失败后的内存及磁盘分离；未知旧档保护；同日/跨代加载；取消一个追踪后重载不复活。

只有修复与真实差异一致才能称为该场景修复。未取得用户原档时可以说故障模型通过，不能说该磁盘旧档已恢复。测试层级与最终增量交付见[回归与发布](regression-and-release.md)；素材范围见[经验案例](maintenance-lessons-2026-09.md)与[来源](sources.md)。

## 7. 负整数与“加载正常、之后保存失败”

新的用户日志明确显示`settings.components.buffs.y: number(-2) vs number(0)`，并有`durableFail=3`但证据列表`failed=0`。前者证明该比较边界两侧不同，不证明磁盘一定把负号吃掉；没有该次原始LoadData表就不能定位Native内部。若采用现有保留前缀保护负整数，仍要验证正常负值、-1/-2、正值/零、小数、大值、保留前缀冲突、旧编码往返及下次加载；不修改用户坐标来通过检查。

故障导出应覆盖加载失败、后续耐久写失败和读回失败，而不只枚举load fence。历史失败次数、当前未解决失败和最近成功需要分列；后续成功可解除“当前失败”，不能抹掉历史事故。导出的是受限原生读快照，不是原始磁盘字节，不为导出运行迁移/修复写入。

修改发行默认值前，额外检查默认补齐是否参与旧canonical。先验证旧schema再应用新默认/迁移；完整闭环见[HUD默认值](hud-template-and-defaults.md)。
