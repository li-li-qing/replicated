# 反馈与逐步蒸馏

用户可以直接发故障描述或现有反馈文档，不必先填写所有字段。Agent 先从材料和代码补齐能读取的内容，只追问阻碍下一步判断的信息。

## 一条可复用记录

```text
案例编号/简短标题：
预期行为：
实际症状与最短触发步骤：
适用环境：服务器、客户端更新日期、插件实际加载版本；相关旧数据版本
证据：日志/报告/源码位置；采集时间；同次报告范围与缺失项
原因：已证实的因果关系；尚未确认的假设单列
修复：变更位置和为何能处理原因；是否仅临时缓解
验证结果：原场景、相邻正常场景；源码/模拟/游戏实测分别记录
剩余问题与下一项能区分假设的检查：
```

屏幕表现异常可补窗口类别、缩放、开关与重载过程；统计问题补时间窗口、单位范围和数据来源；存档问题补格式版本与只读差异。仅在与原因有关时增加信息，不要求用户上传无关个人数据或整份工程。

## 收录标准

| 阶段 | 可以写进什么结论 |
|---|---|
| 候选 | 症状和假设，不能写成“必须这样修” |
| 源码/文档核对 | 指定版本的契约和实现；记录冲突与范围 |
| 本地模拟通过 | 指定输入与模拟模型下的结果，不冒充 Native 实测 |
| 游戏内验证 | 明确客户端、加载版本、操作和结果；不外推到其他服务器 |

反馈来后先判断：原失败是否仍存在、补丁是否实际加载、此次报告是否覆盖该问题。验证器修复、存档恢复和 UI 恢复分别记录成功或待验证。

每次新增规则先找现有主题，原位修正旧结论及其适用日期，增加一个能暴露同类错误的用例。只有新主题才新增参考文件，不留重复“最终版”“新版2”或源码备份目录。保留来源与验证历史，但不复制无关项目全文。

通用的调用、数据和生命周期结论进入对应参考；Replicated Suite 独有的 owner、Store、页面和当轮进度留在项目知识。未证实的恢复猜测不升级为跨插件规则。

以后用户要完善本技能时，以反馈为输入更新相关正文、来源和用例，再做结构检查与有针对性的行为对比。没有新验证结果就维持待验证状态，不制造“已解决”记录。

## 连续失败中的归因与停止条件

每条反馈记录四项，不混成一个“还没修好”：**代码是否加载、证据是否完整送达、故障边界是否已复现、原场景是否通过**。同一全局版本号可能对应多个增量；根据局部标记/内容核对。`rawStatus=copy_budget`是生成端省略，`tries=0`是未验证候选，不能怪用户没复制或用过期文案说已穷举。

至少两类假绿必须写进负例：mock绕过真实Diff/EventBus/Measure，合成存档只覆盖一种数值损失模型。没有真实样本的Store，不因相邻模块已恢复就记为解决。连续多轮相同失败且没有新证据时，停止同类猜修，先打通能区分原因的最小取证边界；不要重复索取相同Hash。

## 用户语义更改也要入库，但不伪造技术事实

明确“冻结=持续留存”“打印后显式上一页/下一页”的后续要求替代本轮早期设计；它们作为项目行为契约记录，而不是宣称所有插件都该这样。Transport4按Store选择、拍卖批次数字、构建标签是源码快照，不升级为通用常量。

经验条目应给出触发前提、可观察失败、实际符号/最小代码形态、修正契约、反例和证据等级。不要只写“要注意性能/稳定性”。本轮提炼索引见[维护案例](maintenance-lessons-2026-09.md)，可直接从其中跳到相关主题。

技能升级本身的验证也分层：结构/链接/复制可读、案例覆盖审阅、独立Agent基线—加载技能对比、实际游戏验收。只运行结构脚本或自己审阅不能宣称模型行为改善；无Agent执行条件就保存情景与评分点并标为待运行，不生成虚构baseline/forward回答。

## 本次Skills维护的可执行成果与未执行项

有三类独立成果：①正文契约覆盖；②工具的正反例执行；③Agent使用技能后的行为效果。不能把①②替代③。本轮新增脚本、合成失败输入和待执行压力题；独立Agent A/B与RU实机未执行。旧案例描述中的“本轮”指其原取材日期，不自动升级为本次验证。

可复用经验优先归入已存在的主题，主SKILL只放触发和门禁。性能数字、具体武器Buff ID、当时HUD模板值放带日期的证据，不硬编码成每次任务都要照搬的行为。原始玩家日志、名称和存档不打进技能；只保留脱敏症状、文件摘要与相关符号。
