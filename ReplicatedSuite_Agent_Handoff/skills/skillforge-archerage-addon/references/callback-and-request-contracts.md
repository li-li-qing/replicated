# 回调、复用与请求确认

用于“已经取消却又执行”“停止后重新注册”“旧结果更新新界面”“收到事件但操作并未成功”。先核对现有机制，按首次失效边界修正；无需为普通功能另建调度框架。

## 分发过程中注册、取消和重入

记录事件、订阅 owner、代次、分发深度以及活动表/待加入队列的状态。单看活动监听器数量可能漏掉尚未入表的订阅。

1. 确定新增监听器在本次、嵌套分发还是下一次分发开始生效。该时机必须是明确契约，不能取决于表的遍历顺序。
2. 若采用延迟加入，取消一个订阅须同时覆盖活动表和待加入队列。否则“回调内注册 B → 随即停用 B → 外层分发结束合并队列”会让 B 复活。
3. 明确嵌套分发结束是否合并，还是只在最外层退出时合并。还要处理回调失败时的深度恢复与队列清理，避免后续事件永远滞留。
4. 不在 `pairs`/`next` 正在遍历的表中随意新增键。可根据现有契约使用延迟变更或稳定快照；快照方案也要核对被取消项是否仍允许在当前轮执行。
5. 对重复注册采用项目既定的替换或多订阅语义，取消时使用实际订阅身份；不能只按事件名清空共享监听器。

Lua 5.1 对遍历期间新增字段的限制见 [next 官方说明](https://www.lua.org/manual/5.1/manual.html#pdf-next)。Ace3 的 CallbackHandler 提供了延迟加入及同时清理队列的实现参考，详见[来源](sources.md)；它的 WoW `securecallfunction` 不是 RU 能力证明。

最小回归：普通分发；回调内新增；新增后立即取消；取消自身/其他 owner；嵌套触发；回调失败后下一次事件仍可处理。先给每种情况写出期望的调用序列，再验证序列，而不只检查最终监听器总数。

## 重复定时器取消

“删除任务索引”不一定使已提交给宿主的闭包失效。核对宿主回调仍持有什么状态，以及重复排期在哪里发生。

- 回调开始前检查取消和 owner/generation 有效性。
- 用户回调可以在执行过程中取消任务、停用功能或更换运行时，所以回调结束后、再次排期前还要检查一次。
- 取消操作应使旧闭包观察到无效状态；重复取消的结果要符合现有契约。
- 区分单调的运行计时与现实时间，核对秒/毫秒。长帧之后是跳过、合并还是补执行，要由业务需求和预算决定；不照搬其他游戏的最小周期，也不无界追赶历史 tick。
- 透传参数时保留 `select("#", ...)` 等价的参数数量；中间或末尾 `nil` 不能被 `#table` 截断。

回归：首次执行前取消、回调内取消、回调内停用 owner、旧代回调迟到、重复取消、长帧和含 nil 的参数。AceTimer 的前后取消检查可借鉴，其 `C_Timer.After`、`GetTime` 与周期限制必须由当前宿主契约替换。

## 池化控件的身份

对象仍存在不等于它仍代表原来的条目。列表、背包格子、团队条在复用后，旧异步查询可能持有同一个控件对象。

绑定时记录当前实体身份、绑定代次和本次请求身份；结果到达时对照当前绑定再决定是否应用。实际接口没有稳定实体 ID 时，明确采用了什么范围内的身份策略，不臆造游戏 ID。

释放时清理本次绑定的事件、数据引用、交互状态和任务；重新获取时设置新条目的完整初始状态。框架负责的锚点/尺寸重置与业务绑定清理分开核对。不要因为框架会池化就假设自定义字段也自动清空。

回归顺序：甲绑定 → 发起查询 → 释放 → 同一控件绑定乙 → 甲结果迟到。期望乙不被污染；再验证乙的有效结果能够正常展示。AceGUI 的释放逻辑和复用测试是检查线索，不代表 RU 具备其 Frame、重设父级或池 API。

## 请求、事件与真实结果

| 阶段 | 必须回答的问题 |
|---|---|
| 计划 | 根据哪份输入快照，准备改变什么？有哪些阻止执行的条件？ |
| 提交 | 调用了什么能力，逻辑返回如何，提交时的对象和代次是什么？ |
| 等待 | 正在等待什么可归因的观测，截止条件和预算是什么？ |
| 确认 | 当前实际状态是否达到了目标，而非仅仅收到一个事件？ |
| 失败/取消 | 结果未知还是已明确失败？下一次动作会不会重复已生效的操作？ |

共享事件可能来自用户操作、其他插件或旧请求。能用请求 ID 时使用；没有请求 ID 时，只使用返回中确实存在的实体、物品类型、品质、单位、范围和时序证据做关联。请求代次只能隔离自己维护的状态，不能凭空证明某个无身份响应属于自己。

无法可靠关联时保留未知，可选择当前允许的串行查询与额外只读核实；“最近一次请求”本身不构成归因证明。迟到、重复和无关事件不能错误推进当前任务。

对团队移动等有副作用操作，事件是重新读取现场的信号。确认目标成员现在的位置，再决定完成或下一步。超时先查是否已经生效；仍无法判定时不要无限重发。每次后续动作重新检查当前能力限制、权限、战斗状态及成员集合，输入改变时停止旧计划或重规划。

纯规划逻辑可脱离游戏进行测试，但“没有游戏 API 调用”不等于“没有输入副作用”。浅复制列表后修改成员表仍会改到调用者输入；验证预览是否应保持输入不变、重复规划是否一致。

回归应覆盖无关事件、重复事件、迟到旧请求、超时但已生效、超时未生效、成员变化、权限变化以及取消。分别记录纯逻辑回放、适配层模拟和客户端结果；不复制其他项目的固定冷却或重试次数作为 RU 通用规则。

## 真实签名与返回值：两种容易被mock掩盖的断点

先读发布端、订阅包装器和最终业务回调，列出实际位置及参数数量。项目总线可能调用 `callback(owner, reason, ...)`，页面写 `function(reason)` 就会把owner当成reason：Native查询和缓存都成功，但“metadata更新”的分支始终不执行。不要把“事件没到”当结论，也不要用每帧重刷绕过参数错误。用真实EventBus测试当前可见页、隐藏页、旧generation和池化行。

区分 `pcall` 的执行状态、回调业务结果、数据false及合法无返回。`ok and result or nil` 会在result为false时抹掉明确拒绝；如果上层把nil当无返回值成功，失败就被吞掉。应按现有API返回契约显式分支，不把所有nil都改成失败，也不重复执行有副作用命令“看看是否真成功”。

测试不仅验证最后状态，还要检查callback收到的owner/reason、显式false是否上达按钮执行器，以及保存成功但UI刷新失败是否被正确命名。参数中存在nil时保留真实数量；这与前述重入/取消是不同断点，需要分别回归。

## 高频事件合并不是尾沿防抖

PVP关键状态连续事件中也必须前进。把待处理原因合并为有限标志集合，并保留首次入队时间与最早期限；只有更紧急事件可以提前，后续事件不能无限推迟。执行前交换待处理表，处理期间新到事件归下一批，避免最后清表丢事件。重排和创建失败须可恢复，不能只有`pending=true`却无任务。

这里不是统一要求50ms，也不需要第二套Scheduler；先读现有机制，再测试真实调度竞争、持续洪流、重入、停用与旧代回调。[PVP契约](pvp-hud-and-freshness.md)负责新鲜度指标。
