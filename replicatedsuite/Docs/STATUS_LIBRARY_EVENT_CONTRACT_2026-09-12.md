## 1. 已确定的代码问题

### 事件参数错位导致内置库停留在旧列表

`core/rs_events.lua` 的 `Publish` 实际调用 `listener.callback(listener.owner, ...)`。
内置库页面却注册 `function(reason)` 并拿 reason 与 management_metadata / tracked_projection 比较。
这个 reason 实际是页面 owner，因此后台已经缓存的图标，以及通过更新事件提交的追踪状态，不能触发库列表刷新。
本轮使用随包真实 EventBus、Scheduler、Api、Store 复现，而不是只把测试回调改成需要的调用方式。
页面现在明确接收 owner-first 参数，按投影 revision 重绘；没有变化的 Aura 事件不会重绑397行或查 Native。
只有控件更新流程成功，页面才确认已显示的 revision，避免一次布局异常让同批数据永远不再显示。

### 临时 API 不可用被当成永久图标未命中

旧服务把能力门尚不可用的读取也记为已完成的负缓存。
现区分暂不可用和正常查询后无图标：能力可用后，下次行绑定可走既有队列重新查询；不另加轮询。
正常没有图标的ID仍负缓存，避免反复滚动造成调用风暴；Aura后来观察到的真实图标可补全缓存并显示。

## 2. 一键导入：已修正与尚未证明的部分

本次直接运行推荐库的真实命令链和持久化流程，空配置一次加入397个去重效果、一次耐久写入、重新加载一致。
**这条成功用例在旧实现也通过。** 因此不能仅凭截图断言用户本次点击的失败原因就是保存函数写错，也不能说本次离线测试已恢复用户这次点击丢失的配置。
确定修正的是已提交追踪状态的事件刷新，以及失败时缺少清晰业务阶段反馈的问题。

新行为：
- 库页独立显示“所选分类数量 / 已追踪数量 / 已取得图标数量”。计数来源为Feature当前已提交选择及共享缓存，不使用实时Aura是否存在来判断追踪。
- 每次导入从validate开始记录结果；未知包、读取保护、容量拒绝、Core保存失败分别保留validate/prepare/mutate/commit阶段。
- 成功后仍打开“已追踪”，清除搜索限制并显示结果；重复导入去重，用户自定义条目不删除。
- 页面命令异常给出可见原因并记录；保存成功但刷新异常明确说“追踪已保存，但列表刷新失败”，不谎称数据已回滚。
- 核心本来已记录通用存档失败；本轮增加包名/导入阶段上下文，不宣称旧版完全没有日志。

服务在既有分页报告中提供最近8个查询的返回类型、至多12个顶层字段名/类型及结果。
不收集tooltip全文，不根据未知返回结构猜图标路径，也不把关联技能图标冒充效果图标。
`X2Ability:GetBuffTooltip(buffType,itemLevel)` 随包参考只支持调用签名，没有给出覆盖所有ID的返回结构保证；每个ID是否实际提供资源仍需RU验证。
图标显示由Native返回/真实Aura学到的路径决定，本包不承诺所有397个条目都有有效资源。

## 5. 使用

完整覆盖本ZIP，再使用插件内“重新加载文件”。不清档、不重置、不要求退出游戏。
打开状态显示内置库，停留等待可见行解析，再点击“一键加入追踪”。成功后应进入已追踪；已有自定义条目会使总数大于397。
如未加入或仍全部未知，复现后打印现有分页报告。报告包含 `libraryPatch="status-library-eventbus-2"`、`lastImport.stage/ok/error` 和 `metadata.resolver.samples`；无需再次上传同一份udf。
