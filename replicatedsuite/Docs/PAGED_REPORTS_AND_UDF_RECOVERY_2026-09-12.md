# 完整错误报告分页与 UDF 实档恢复

日期：2026-09-12。补丁标识：`paged-udf-proof-1`。
基线：本次对话 `Addon(20260912-025223).zip` 及后续到 `ReplicatedSuite_F2_ProtectedPage_EvidenceHandoff_2026-09-12.zip` 的增量。部署时仅覆盖本补丁，不清档、不重置默认设置，不替换用户 udf。

## 1. 用户操作流程

使用插件内“重新加载文件”加载更新代码；复现问题；打开“诊断与维护”；点击“打印自检报告”。界面上方是“运行自检”和“打印自检报告”，下方是明确的“上一页 / 页码 / 下一页”。

打印只生成一次固定报告。报告字符串在内存中完整保留，按原生编辑框实际可往返接收的容量拆成逻辑页。一个原生编辑框复用显示第 1、2、3…页，而不是同时创建 N 个控件。每页分别 Ctrl+A、Ctrl+C，然后发送或依次粘贴到同一个文本文件。

翻页不执行新的自检、不读取存档、不改变报告 ID、不悄悄重新划分页边界、不自动绕回首页。再次打印表示生成新报告并回到第一页。运行自检、关闭页面或重载会释放旧报告，不把上轮报告误作当前报告；运行自检本身不清除本次加载以来的错误历史。

正文页以 `RS-ERROR-PAGE-1` 开头，以 `RS-ERROR-PAGE-END` 结束。原文换行显示为 `\n`，反斜杠也可逆转义，防止客户端吞掉真实换行；这不是加密或压缩。维护端按字节数、报告 ID、页号、偏移及校验重组，还原原始正文。页内出现相同尾标字样不会提前截断，因为解析按声明字节数取数据。

聊天只有一个短回执，不是完整错误报告。不得调用 API 参考中不允许的剪贴板接口。

## 2. 日志与采集边界

复用当前项目的 `S.RecordLog -> DiagnosticsManager:CaptureSelfCheckIssue`，不新增 Tick、事件订阅或第二套业务状态。日志先保留字符串片段与计数，点击打印时才连接成报告，避免每个错误都复制整份字符串。

默认分页报告包含失败检查、已记录的 error/warning、相关运行状态和所有允许取证的写保护 Store 原始表。紧凑取证仅去掉外层重复说明，不删除 Native 原始表字段。旧 3500 字节聚焦格式保留内部兼容，但不再是页面默认；编辑框容量不再决定是否丢弃存档证据。

资源安全上限仍存在且在正文中明确披露：64 种不同错误、每条最多 16 KiB、完整报告最多 1 MiB、每次最多 8 个写保护 Store，每个原始取证不超过已有 Core 限额。相同错误累计次数。因总安全预算、读取失败或上游日志已截断造成的不完整，会显示 coverage/partial 原因；不能承诺收集未经过项目日志入口的客户端或其他插件错误。

当前页默认不超过 3500 字节（包含页头），如原生实际回读更小，在第一页交付前有界缩小；已交付过页面后不改边界。按 UTF-8 边界拆分，中文不在字节中间切断。任何回读不一致都不当成成功。

重载使用项目现有入口；它重建插件的 generation、日志与诊断服务。它不是新游戏进程，但本补丁不要求退出客户端才能加载代码。原有保存失败也可继续重载的修复逃生路径未修改。

## 3. 本轮真实 udf 证据

对上传 `udf.zip` 的只读副本进行分析，没有打开可写数据库，没有更改 CURRENT/MANIFEST/SST/log，也不把其他插件配置打进交付包。按 CURRENT 指向的 MANIFEST 活文件集合、序号与删除标记确定当前值，并检查读取块和日志记录的 CRC32C。没有把 `lost/` 或较旧值冒充当前配置。

从当前记录读出三个 Store 后，按真实 Core/Store 进行解码和校验。实机报告与离线原文数值吻合：

| Store | 原章 | 当前重算 | 历史验证结果 |
|---|---|---|---|
| 状态显示 | `1E7F5813` | schema6 `6307A930`；schema5 `6623AE99` | 单一中心 X 的旧 token 恢复后精确命中 `1E7F5813` |
| 死亡回顾 | `695423CD` | `3B54171E` | 四个 history time 的非整数 token 恢复后精确命中 `695423CD` |
| 跑商 | `6BE9E557` | `6BE9E557` | 现有 Transport 3 已正常 |

死亡回顾的科学计数格式在本机 libc 与实机报告之间存在不同。测试单独使用三位指数呈现模型（例如 `e+006`），可以复现实机指纹；该模型只在测试环境使用，没有全局替换生产 `string.format`。不能因此声称运行了 Windows 或 RU 客户端。

### 状态显示

实际 `widgetWindow.normalizedCenterX = 0.82991701364517212`，旧六位有效数字 token 为 `0.829917`。整份 schema5 原章要求的 token 是 `0.829918`。

可以由这样的独立损失模型产生：源数字在 `0.8299175` 附近，先投影为 binary32，再保存固定六位小数，随后读取为 binary32；这会跨过旧六位有效数字的舍入边界。此前只模拟“固定六位小数 -> binary32”，遗漏了先行投影。

新增分支仍只处理已有的两个中心比例、每次仅一个字段、完整旧章唯一命中、总计至多 32 次指纹验证。候选原数字必须能通过明确损失模型投影回实际读取值。**候选只用于旧章证明，实际加载的窗口数值仍保留本次读出值，不把某个候选小数宣称为找回的原值。** 原有跑商 fixed6 分支兼容行为保留。

### 死亡回顾

实际索引有 20 条摘要。部分 `history.entries[].time` 投影为 binary32 后变成整数，旧指纹算法却对整数使用 `%.0f`、对非整数使用 `%.6g`，从而改变 token。

只在 schema2/framework3/transport2/codec1、完整序列且原始业务树与当前 canonical 逐项一致的情况下，检查最多 8 个范围内的整数 time（最多 255 个子集）。每个非整数见证点严格处于同一个 binary32 舍入单元中；整份旧章唯一匹配才返回候选。此次真实样本 5 个合格时间值，31 个非空组合中唯一命中，涉及 4 个 time token。

返回给业务模块的 Domain **仍是原始读取的时间、顺序、来源、伤害和其他字段**，不编造丢失的小数，不读写单条 record 分片，不扩大到其他数字。缺失/多余字段、稀疏序列、无匹配、多匹配或超预算继续写保护。

### 恢复后的保存

Store schema、业务指纹算法、保存键和 Transport 3 均未再次升级。Core 验证历史候选后迁移并应用原读数据，在后续保存时用当前 canonical 重新盖章；Transport 3 继续保护数值传输。

离线实档验证中，两份旧档均加载成功；加载阶段零 SaveData/ClearData。状态显示只进行已有 schema5→6 迁移，死亡历史 20 条及所有原读字段保持一致；随后保存、物理回读验证和模拟插件重新注册后的读取均成功。这个结果不等于已通过 RU 游戏内验收。

现有指纹是项目的一致性校验，不是密码学认证。本轮没有添加这两组用户 Hash 白名单，没有降低指纹精度，没有跳过 Envelope/身份/容量检查。
