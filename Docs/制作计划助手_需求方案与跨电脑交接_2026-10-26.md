## 1. 用户问题与原始要求

### 1.1 使用场景

游戏按 O 打开的制作查询页面可以查询物品、成品及材料，但多层配方的实际制作准备非常麻烦：

- 一个物品可能有五六层材料。
- 查完配方还要切到拍卖行，记住物品名字再搜索。
- 同时记住多层材料数量、当前价格和制作劳动力，负担很大。
- 数量变化时需要重新算。
- 很难直观看出中间材料直接买便宜，还是继续买原料自己制作便宜。
- 多个目标共享材料和库存，容易重复计算。

用户已在自己的项目中使用过两类相关能力：

1. 拍卖收藏：点击某个材料，可以搜索，方便购买。
2. 跑商：双击货物，可以查询相关材料价格并保存在本地，方便之后查看。

这些是用户描述的现有体验。当前源码也存在相关服务，但另一台电脑上的最终实现状态需要现场重查。

### 1.4 目标闭环

添加目标物品和数量 → 读取配方 → 统一抵扣可信库存 → 分配购买/制作数量 → 展开制作分支 → 合并采购和制作批次 → 显示金币与劳动力 → 比较路线并给建议 → 点击材料进入拍卖搜索 → 用户主动校准价格。

### 2.2 用户明确提出的功能与硬约束

- 多层配方递归，不局限一级材料，必须覆盖五六层常见制作链。
- 输入目标数量后自动重新计算数量、金币、银币、铜币和劳动力。
- 每层都能决定买中间材料，还是继续自己制作。
- 购买部分不再展开成当前计划的下级需求；制作部分继续展开。
- 材料名称/图标可触发对应拍卖搜索，减少记名和手动输入。
- 已有材料足够绿色，不足红色；劳动力足够绿色、不足红色。
- 对比从基础原料制作与直接购买成品的价格。
- 考虑价格变化，重视本地持久保存。
- 不能每次打开、展开、改数量都查询拍卖。
- 用户主动再次查询、人工校准价格。
- 必须解决箱子库存重复读取、堆叠和计划分支重复抵扣。
- 本机不是最新项目，不能据此直接回写另一台电脑。

### 4.3 两个关键反例

反例 A：不同分支都使用同一可制作中间材料。第一个分支展开了该材料配方；后一个分支不在同一递归路径上，却因全局 visited 被挡住。其结果可能漏掉子材料。

反例 B：两个分支各需要 10 个中间材料，现有库存只有 10 个。若先让两个分支各自看到这 10 个，下级需求都会被算成 0；之后再分配共享库存，第二个分支虽然缺 10 个，下级原料仍可能保持 0。

这些反例用于设计和后续复现；本轮没有运行参考插件，也没有把用户实际遇到的全部 bug 归因到上述位置。

- 不把配方未知、不可交易、制作门槛不符的对象强行加入可执行推荐。
- 不预设副产物套利、跨市场搬运或全局最优交易策略。

### 5.3 候选工程路线

| 路线 | 做法 | 优点 | 风险/结论 |
|---|---|---|---|
| A | 直接修补/移植 craftinglist 单文件 | 表面上较快复用现成 UI | 库存、身份、批次、价格、生命周期需大量重做，不建议作为正式基础 |
| B | 在最新 Replicated Suite 中复用服务，新增独立计划计算与投影能力 | 能统一拍卖队列、持久化、库存边界和交互风格 | 推荐方向；必须先核对最新代码，不能预先承诺文件结构 |
| C | 长期维护独立制作 Addon | 可以不依赖 Suite | 重复建设查询队列、保存和库存治理，与现有便利入口割裂；只有用户明确要求独立发布时再评估 |

这是助手的工程建议，用户没有单独选择 A/B/C 工程路线；不要与 SkillForge 协作等级混淆。

建议先以可丢弃的确定性计算模型证明规则，再在最新 Suite 接入一条最小真实链路。可丢弃模型也要在获得实施/原型授权后才创建。

## 6. 核心概念、身份与数据所有权

### 6.1 概念

| 概念 | 含义 |
|---|---|
| 目标行 | 用户想准备的物品、品质/适用条件和数量 |
| 物品身份 | 可用于配方、库存、交易匹配的真实物品标识，不是展示名称 |
| 配方身份 | 一个具体制作方式；同物品可能对应多个配方 |
| 需求发生位置 | 一个目标/分支为什么需要这种材料，供树展示和解释 |
| 汇总需求 | 同一兼容物品在整份计划中的合计需求 |
| 库存分配 | 从可信库存中为本计划需求实际分配的数量 |
| 购买需求 | 用户分配给拍卖购买的缺口 |
| 制作需求 | 用户分配给手工制作的缺口，不等于制作次数 |
| 制作批次 | 考虑每次产出、门槛、配方和上下文后需要执行的次数 |
| 采购预算 | 根据参考价或可读取挂单计算的预计支出，不是交易保证 |
| 推荐方案 | 固定输入版本下生成的候选，不修改用户手动方案 |

### 6.2 身份规则

- 展示名可变、可重复、可本地化，只用于显示与搜索提示。
- 材料合并至少考虑真实物品 ID；品质、绑定/交易限制、用途限制等按实际配方契约决定是否可互换。
- 不能把 itemId、itemType、craftType 等不同含义的数字随意互作兜底。
- 内部 UI 行 ID、计划行 ID 与真实物品 ID 分离。不要用虚构负物品 ID 冒充可直接查询库存的真实物品。
- 同物品的不同配方不等于重复错误，必须保留候选和选择依据。
- 同名但身份未确认的数据保留歧义，不参与确定抵扣。
- 物品只能绑定在角色、服务器、市场、品质等经验证适用的作用域中，不能跨作用域复用旧价和库存。

### 6.3 所有权建议

| 层/职责 | 拥有的数据 | 不应做的事 |
|---|---|---|
| 原生适配/能力边界 | 经许可的读取与原始结果 | 绕过能力限制，凭 pcall 成功宣称可用 |
| 配方服务 | 规范化配方及来源、版本、解析状态 | UI 刷新时无界扫描整个目录 |
| 库存服务 | 背包/仓库观察快照与可信度 | 为每条树分支复制一份全局库存 |
| 价格服务/查询队列 | 报价事实、保存、请求关联和队列 | 每个功能另建拍卖通道 |
| 计划计算器 | 固定输入快照到结果的确定性计算 | 计算过程中发拍卖查询、读写控件或修改真实物品 |
| 计划功能层 | 用户目标、混合分配、选配方、采纳推荐 | 把 UI 展开状态当作业务来源 |
| Presentation/UI | 树、采购清单、制作步骤、颜色与操作入口 | 保存第二份库存或自行累加成本 |

具体名称及文件拆分由最新工程决定，上表不是拟新增文件清单。

### 6.4 建议的数据快照

建议包含以下信息，但字段名不是已存在的 API：

- Plan：计划 ID、版本、目标行、来源分配、选配方、劳动力折价设置。
- Recipe：配方 ID、产物身份/每次产量、材料与每次用量、劳动力、手续费、门槛、来源和解析状态。
- InventorySnapshot：角色/来源作用域、容器上下文、槽位、物品兼容属性、数量、采样时间、完整性、会话代次、核对状态。
- PriceObservation：物品/市场身份、价格类型、货币单位、单价或整组总价、样本数、挂单数量、观察时间、来源、覆盖状态、异常候选状态。
- Evaluation：输入版本、需求、库存分配、采购项、制作批次、余料、金币、劳动力、未知项、截断原因。
- Recommendation：输入版本、候选变更、节省范围、劳动力变化、依据完整度和适用状态。

## 7. 库存快照、去重与共享抵扣

### 7.1 三层问题必须分开

1. 读取去重：同一次库存事实不能因重复回调或重新打开被算多次。
2. 库存汇总：两个真实槽位/容器的合法堆叠需要相加，不能误去重。
3. 需求分配：多个目标和分支共同使用一份库存，不能分别拿全部库存抵扣。

“同名取最大值”不能同时解决这三层问题。它既可能误合并不同物品，也可能丢掉合法的第二个堆叠。

### 7.2 快照替换规则

- 在来源身份和采集完整性已确认的条件下，保存该来源的完整快照。
- 再次读取同一来源时替换旧快照，不把新扫描数量累加到历史数量。
- 只有完成并验证的扫描才作为完整快照提交；扫描中断不应把未读槽位写成空。
- 正确处理合法零数量和空容器；不能因保存系统省略零值而复活旧库存。
- 同来源旧代次结果晚到时丢弃，不覆盖较新快照。
- 部分增量更新只有在接口语义可证实时才使用，不能把增量当总量或总量当增量。
- 本地保存的仓库数据是历史观察；重载后若未再次核对，保留时间和待核对状态。

### 7.3 容器身份是待验证能力

不能假设游戏一定提供稳定的箱子 ID。

- 如果接口确有可靠稳定身份，按已验证契约区分箱子与槽位。
- 如果只有当前打开窗口的上下文，只能证明会话内的来源，不能生成一个看似稳定的 ID 永久合并。
- 无法证明两次打开的是同一箱或不同箱时，不允许静默把两次快照相加。
- 降级方案可以是用户明确选择“更新已有箱子记录/登记另一箱”，带核对状态；具体体验需在接口探针后设计。
- 本机藏宝图库存代码包含登记箱号和识别会话逻辑，只能提供思路，不证明通用仓库有稳定原生身份。
- 用户 D-07 确定了背包＋仓库；是否包含可交互的独立保管箱、哪些箱子算仓库，需现场列出实际类型并确认，不默认把世界所有箱子都算个人库存。

### 7.4 转移、拆堆与合堆

- 30＋20 两个合法槽位应汇总为 50；同一槽位读取两次仍是其最新数量。
- 50 拆成 30＋20，总量不变。
- 30＋20 合为 50，总量不变。
- 箱子转出 20 到背包，总量不应因“新背包＋旧箱子”短暂增加 20。
- 若移动事件可靠，按其语义标记受影响来源并同步/复核。
- 若移动发生时仓库不可读，旧仓库快照应标待核对；不能继续作为确定库存与新背包相加。
- 推荐默认：确定库存用于绿色状态与确定缺口；未核对记录单列为“可能已有”，不能冒充已备齐。这一降级展示为 P-06 建议，需要在实际交互中确认。

### 7.5 全计划共享分配

设同一兼容物品的总需求为 D，可信可用库存为 H：

    库存抵扣 A = min(D, H)
    剩余缺口 S = max(0, D - A)
    各分支分配之和 <= H

多个分支的需求可分别展示，但必须来自同一分配账本。

例：武器需 40 原木，防具需 30，可信库存 50：

    总需求 = 70
    库存抵扣 = 50
    剩余缺口 = 20

不能让两个分支各抵扣 50。不能仅靠汇总页“修正总数”，却让左侧树仍沿错误缺口展开。

默认分配顺序建议稳定且可解释，例如按目标顺序，背包先于仓库；此顺序属于实现建议。无论显示分配顺序如何，最终采购量、批次和成本都应一致，除非用户明确为分支设置不同配方/来源约束。

不同计划同时存在时，首轮只对当前计划内部共享抵扣；不默认建立跨计划永久预留系统。若以后增加“多个计划同时执行”，需单独定义全局库存占用。

## 8. 配方展开、混合来源、批次与劳动力

### 8.1 展示树与计算依赖图分离

树用于告诉用户“这个材料为什么需要”；整计划计算需要识别共享节点，不能每棵树独立计算后简单相加。

- 路径集合只用于检测当前链上的循环。
- 配方元数据缓存用于复用已读配方，不应阻止其他分支引用。
- 同一材料作为目标和作为另一目标的中间材料时，需求要合并核对。
- 深度、节点数、数量和计算工作量必须有界；达到上界显示“结果不完整”，不能自动判定为基础原料。
- 确实无制作配方、配方不可访问、解析失败、存在循环，是不同状态。

### 8.2 混合数量规则

用户例子：

    总需求 20 木材
    已有可信库存 5 木材
    缺口 15 木材
    用户分配：购买 10，制作 5

基本不变量：

    购买需求 B >= 0
    制作需求 C >= 0
    B + C = 剩余缺口 S

分配不足、超量、负数、非整数、溢出必须有明确反馈。需要表达主动囤货时应另设额外采购目标，不要靠静默接受超量混合分配。

- 购买 10 的分支停止当前需求展开。
- 制作 5 的分支继续计算配方、材料、批次和劳动力。
- 购买的中间材料与其下级原料不能在当前方案中同时计费。
- 用户锁定的购买数量不应被推荐或价格校准悄悄改写。
- 数量变化后如原分配失效，应显示待调整或明确的重新分配规则；不要默默保留不一致结果。

### 8.3 制作次数与余料

设净制作需求 C，每次产出 Y：

    制作次数 K = ceil(C / Y)
    实际产出 P = K × Y
    剩余产物 E = P - C
    某材料需求 = K × 该配方每次材料用量

例：需求 5，配方每次产出 3，需要 2 次，产出 6，余 1；不是制作 5 次，也不是制作 1.667 次。

若多个分支使用同配方且制作条件相容，先合并它们的制作需求再向上取整。例如两处分支各需 1、每次产出 3，整计划可制作 1 次覆盖 2，而非各做 1 次。

不能合并不同品质、不同绑定条件、不同配方或其他不可互换产物。余料若在当前计划内部继续被其他需求使用，应只分配一次；未使用余料单列，不自动当作已经卖出获得金币。

### 8.4 建议计算流程

1. 固定本次输入：计划版本、配方版本、可信库存版本、价格版本、角色/制作上下文。
2. 验证目标、数量、身份、来源分配和选配方。
3. 解析所需可达配方图，标记未知、循环、多配方歧义和上界截断。
4. 在产物到原料的依赖顺序上汇总同一兼容物品的全部需求。
5. 从统一库存账本分配可用量，得到缺口。
6. 应用用户购买/制作分配，将兼容制作需求归入同一批次组。
7. 计算批次数、余料及下级材料需求，继续依赖传播。
8. 收敛采购清单、仓库取用清单、制作步骤、费用和劳动力。
9. 检查物料守恒和完整度后发布一个结果版本，UI 统一消费。

这是算法约束，不是要求用某个具体算法逐行实现。接手者应避免“边深度遍历边占用库存边各自取整”造成结果依赖遍历顺序。共享中间材料的所有上游需求必须到齐后再确定批次；更改高层来源后，重新计算受影响子图。

复杂多产物配方、循环转换或多配方联合最优化不保证能直接套上述普通 DAG 流程；首轮发现时明确标支持边界，不猜一个产物成本分摊系数。

### 8.5 劳动力与制作费用

- 累加所有实际需要执行的制作批次，包括各级中间材料和最终成品。
- 直接购买的部分不消耗该部分制作劳动力。
- 已有中间材料抵扣后，只对剩余制作数量计未来劳动力。
- 劳动力必须采用该角色/配方/实际上下文可核验的有效消耗，不能永远把基础说明值当实际值。
- 如存在熟练度、增益、制作台、折扣或其他修正，需要验证具体规则；本轮未证明这些 API 和算法可得。
- 可能存在额外制作金币、商店材料、绑定货币或工具消耗，实际配方有则单列；未知不能默认为免费。
- 当前可用劳动力、需求劳动力、缺口分别显示；读不到可用劳动力时显示未知，不能显示 0 或“不够”。
- 计划展示不足劳动力仍有价值，但推荐须标“当前无法一次完成”；是否以当前劳动力作为推荐硬上限见第 16 节。

## 9. 成本、估值、路线比较与推荐

### 9.1 两种主金额不能混淆

用户已确认：

1. 还需支出：抵扣已有材料后，完成计划预计还要支付多少金币。
2. 完整估值：已有材料不是免费，也保留其参考价值。

这不意味着“全部从零买一遍”和“把已有材料估值”是同一个数字。

建议把金额明确拆成：

| 金额 | 建议定义 |
|---|---|
| 参考需求成本 | 当前路线实际需要的新购数量 × 参考单价，加必要制作费用 |
| 买齐预算 | 在已观察挂单范围内，为满足采购数量需要实际支付的整组金额，加制作费用 |
| 已有材料占用价值 | 本路线实际抵扣的库存数量 × 对应参考价值；同一库存只计一次 |
| 完整估值 | 已有材料占用价值＋新购材料的消耗价值＋制作费用 |
| 还需支出 | 本次新采购现金支出＋后续制作费用 |
| 综合成本 | 对明确标注的金额口径加上本次未来劳动力折价 |

这是补足数学定义的建议，不是已经逐项确认的会计政策。尤其整组采购余料的价值，应与现金支出分开列示：

- 为买 5 个而必须买一组 10 个，现金支出按 10 个算。
- 当前计划消耗 5 个，另外 5 个列为采购余料。
- 完整消耗估值与现金支出可能不同；不能把多买的 5 个既作为本计划消耗又作为余料价值。
- 不自动抵扣“未来出售余料”的收入。
- 如果首轮只实现参考价估值，应明确说明其不等同真实成交成本。

正式实现前应确认“完整估值”的最终标签和余料口径，不能用一个含糊“总成本”覆盖所有数字。

### 9.2 劳动力折价

- 未设置每点劳动力价值时，显示金币差和劳动力数量，不生成虚构汇率。
- 设置后额外显示综合成本，保留原金币和劳动力。
- 折价只影响经济比较，不改变角色当前劳动力或配方真实消耗。
- 历史取得库存时消耗过多少劳动力通常未知，不在本次未来劳动力中重复追算。
- 劳动力折价值和计算口径需要随计划保存；更改后仅本地重新计算，不查询拍卖。

### 9.3 比较路线

| 路线 | 规则 |
|---|---|
| 当前手动混合方案 | 按用户选配方和各材料购买/制作分配计算 |
| 基础原料制作 | 对可可靠展开的制作链持续制作，直到真实可采购基础输入；不能把未知配方当基础原料 |
| 直接购买成品 | 购买各目标成品，不再计其制作材料和制作劳动力 |
| 推荐候选 | 在已知且可行的购买/制作选择中比较，用户采纳前不修改当前方案 |

比较必须锁定相同目标数量、品质/用途、库存快照和价格快照。每条候选路线独立从同一初始库存重新分配；不能把第一条路线用掉的库存留给第二条，也不能让路线共用同一份可变计算账本。

建议同时展示：

- 金币预计差额。
- 未来劳动力及其变化。
- 可选综合成本差。
- 需要取出的仓库材料。
- 制作批次数和余料。
- 缺报价、旧价、配方未完整等影响结论的原因。

“基础原料制作”存在两个解释：抵扣当前库存后补齐，或完全从零采购制作。建议默认按当前库存显示还需支出，并另提供从零参考估值；最终标签需按第 16 节确认。两条比较路线必须使用同口径，不能一条扣库存、另一条不扣后宣称省钱。

若成品不可交易、无有效挂单或身份不匹配，直接购买路线显示不可用/暂无报价，不显示 0 成本。

### 9.4 推荐行为

已确认推荐由用户采纳，不自动覆盖。

- 说明推荐改变了哪些材料的购买/制作数量。
- 说明预计节省多少金币，以及劳动力增加/减少多少。
- 有劳动力折价时说明按哪种综合口径比较。
- 缺关键数据时不给确定“最低价”结论，可展示有条件建议。
- 旧价可用于带时间标签的参考建议，不能冒充实时可买到。
- 支持逐项采纳和整套采纳；采纳前校验版本，避免把旧输入的建议应用到新计划。
- 建议提供撤销；具体历史深度不预设。
- 价格校准后生成新建议，但不自动应用。

不能简单对每个节点独立比较一个单价，就宣称整计划全局最优。共享库存、制作批次、整组挂单、不同配方和劳动力约束会产生联合影响。

首轮可以给出有界候选比较，必须标为“已比较候选中的建议”，不承诺所有路线全局最优。算法复杂度、候选上界和取消点由实际数据验证。

## 10. 拍卖搜索、价格保存与人工校准

### 10.1 两档价格

快速参考估价：

- 使用本地已确认的单价记录。
- 说明是样本参考价、采样时间及品质/市场适用范围。
- 参考单价乘需求数量，不代表挂单足够。
- 本机现有严格报价链读取当前搜索结果最多前三条有效样本；不能将其包装成全市场最低价。
- 最新电脑的实际策略仍需复核，不为了新功能静默扩大既有跑商查询范围。

主动买齐预算：

- 用户明确触发更深入的数量/挂单检查。
- 根据能可靠读取的挂单总价、整组数量和购买规则计算预算。
- 考虑便宜档数量不够、后续更高价格和必须整组购买的多买部分。
- 读取到的挂单覆盖不足时，显示已覆盖数量和剩余缺口，预算标未完整。
- 即使观察时覆盖足够，也不是实际成交保证；挂单可能被别人买走。
- 不允许同一挂单因跨页、重复回调或重复查询被计算多次；缺少可靠挂单身份时说明去重和覆盖限制。
- 完整市场抓取、翻页、排序可信度及整组购买语义都尚未验证。

### 10.2 日常行为不触发拍卖查询

以下操作只使用本地数据重新计算：

- 打开计划、切换计划。
- 展开/收起材料树。
- 修改目标数量。
- 调整购买/制作数量。
- 切换成本口径或路线。
- 更改劳动力折价。
- 打开诊断、查看说明、刷新 UI。

库存或配方按经验证事件更新，与“是否发起拍卖查询”是不同职责；不能为了阻止拍卖扫描而冻结实际库存变化。

缓存过期本身只改变状态提示，不自动为本制作计划入队搜索。首轮缺价也先显示待报价，不默默触发一整套查询。

### 10.3 明确触发动作

建议动作名称：

- 搜索此物品：玩家前台搜索，便于自行购买。
- 校准此项价格：查询并尝试更新该物品参考记录。
- 校准本计划所需价格：有限、去重的明确批次，展示待查项目。
- 计算买齐预算：独立的深度动作，明确范围与覆盖。
- 取消本次查询：停止未发送任务，已进入原生调用的任务按实际能力隔离回执。

玩家自行搜索某物品，不代表可以把当前返回结果写给任意等待中的材料。必须关联物品身份、品质、请求归属和代次。

### 10.4 持久价格信息

至少保存或可还原：

- 物品和品质/兼容属性。
- 服务器、市场或其他实际价格作用域。
- 货币与最小单位。
- 单价、整组价格、整组数量的区别。
- 参考价来源与样本数。
- 采样时间，使用能跨重载解释的时钟。
- 当前价、过期参考、未查询、无匹配挂单、接口不可用等状态。
- 买齐预算的需求数量、覆盖数量、采样窗口和适用版本。
- 异常跳价是否仅为候选、是否已确认。

不能把跨天缓存年龄建立在重载后归零的会话毫秒上。不能把“无挂单”永久缓存为零价格。

### 10.5 复用现有价格服务时的关键冲突

本轮读取的 rs_material_price_service_v3.lua 具有：

- GetPrice/GetTradePrice 本地读取接口。
- QueueRevalidate 后台更新入口。
- 持久价格、时效分层、异常价格保护、owner 生命周期和有界容量。

重要：服务支持后台刷新，不代表本制作计划应该自动调用。接手者必须追踪实际调用链，保证“打开页面/读取旧价”不会隐式调用 QueueRevalidate。

其他现有功能可能仍按自己的既定规则刷新同一共享价格库。不要为了制作计划的“主动校准”要求全局删除其他功能的行为。制作计划可以接收共享库的新价格，标注更新时间并重新计算，但不得因此自动改变用户路线。

已有异常保护若把跳价保留为候选，手动点击也不应无提示绕过。可显示旧确认价、新候选和“需复核”；如何人工确认异常值是独立交互，尚未明确授权“任何一次手动搜索都强制覆盖”。

### 10.6 有界调度与低干扰

- 复用最新工程的唯一拍卖查询队列和用户优先级。
- 同物品、同品质、同目的的重复点击去重/合并，不重复入队。
- 列出批次任务数与上界；最多页数、样本数、超时、重试等应基于当前 API 和实测，不能把旧间隔当万能参数。
- 玩家手动操作拍卖时让出或暂停后台批次，避免覆盖其关键词和结果。
- 取消、关闭、切换计划时取消本 owner 的等待任务，并隔离旧代次回执；不误取消其他消费者。
- 查询结果更新可合并发布，避免每条价格返回都重扫所有库存、配方和 UI。
- 有间隔/分帧不保证单次原生调用不阻塞；应分别测量原生调用、解析、重算与渲染耗时。
- 不能创建无限轮询、无限回退搜索或失败后永不停止的重试。

## 11. 交互与状态呈现建议

本节是文字交互草案，不是已实现 UI，也不是已完成视觉验收。沿用最新项目获认可的主题和控件，实际布局后续可做可丢弃原型供用户评审。

具体单击/双击组合尚未确认，应在最新 UI 中验证焦点和既有行为，不凭参考插件直接套用。

## 12. 持久化、生命周期与性能边界

### 12.1 持久化内容

建议分离：

1. 用户计划：目标、配方选择、来源分配、劳动力折价与设置。
2. 价格观察：复用共享服务，计划不另建不一致的价格真相。
3. 库存历史观察：来源身份、时间、完整性和待核对状态。
4. UI 偏好：展开状态、列布局等，不能影响业务正确性。

不保存原生控件引用、当前窗口对象、会话代次当永久身份，也不把过期库存自动升级成实时库存。

- 使用最新工程 Persistence/Store 和已有 codec。
- 零值、false、空表、稀疏列表需要按实际序列化往返验证。
- 读取失败/未来 schema/完整性异常时保留原记录和明确提示，不能静默清空计划。
- 迁移用户计划与可再生成的价格缓存是不同风险，不能共用“损坏就重建为空”的策略。
- 不照搬参考插件的绝对文本路径和分隔符协议。

### 12.2 生命周期

- 每个查询批次有 owner 和 generation。
- 切换计划、撤销采纳、更换角色上下文后，旧推荐与旧异步结果不能覆盖当前计划。
- 功能停用后释放自有订阅、调度任务和控件引用。
- 隐藏窗口与禁用功能分开，是否继续当前明确查询应有一致规则；建议关闭可见计划时停止其非必要查询，具体遵循最新项目约定。
- 共享服务仍有其他消费者时，不全局清掉缓存或任务。
- 已接受报价可以更新其正确物品的共享记录，但不能写入错误计划或唤醒已关闭 UI。

### 12.3 性能原则

- 数量、来源、库存、价格变化分别失效对应计算，不用每帧全图重建。
- 配方结构与动态数量、库存、价格分开缓存；不能长期缓存读取失败结果。
- 查询、解析、计算、投影与绘制分别衡量。
- 对实际大计划使用有界遍历、批处理和列表复用；达到上界可解释。
- 先以真实慢点和实际规模选择优化，不承诺某个毫秒预算已经达成。
- 推荐不随每次鼠标展开重新穷举；输入版本不变可复用结果。
