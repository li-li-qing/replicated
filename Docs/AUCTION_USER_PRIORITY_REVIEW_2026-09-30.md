## 1. 完成内容

### 1.1 根因：后台材料名称搜索与原生界面共用结果通道

检查到的实际调用链为：

```text
Trade:QuoteMaterial / MaterialPriceServiceV3 缓存后台刷新
  -> PriceQuoteQueueV3
     -> AskMarketPrice(itemType, itemGrade, false)
     -> GetLowestPrice(itemType, itemGrade)
     -> 稳定 ID 价格不可读时进入 BeginSearchFallback
        -> AuctionQueryV3:Search("price_quote_fallback", keyword, ...)
           -> X2Auction:SearchAuctionArticle(...)
```

旧 AuctionQuery 只序列化插件内部请求，没有检查玩家是否正在使用原生拍卖行。因此每次材料名称兜底搜索仍会替换原生结果，下一项材料又继续搜索。问题不只是文字框被设置，而是底层共用搜索结果通道被反复使用。

同时，AuctionSurface 的常驻观察随拍卖助手消费者启停。关闭拍卖助手后，缓存 snapshot 里的 `idle/stopped/visible=false` 不能证明原生拍卖行没有打开。仅检查缓存或仅修拍卖助手按钮都覆盖不到该场景。

### 1.2 新的搜索优先级

- 原生拍卖行可见：后台材料名称搜索暂停，不继续发 `SearchAuctionArticle`。
- 原生可见性无法确定：保守等待，不把未知等同“关闭”。
- 明确关闭且没有用户查询/旧回包隔离占用：按已有 1000ms 队列节流恢复。
- 直接按物品 ID 的原查询路径与已有有效价格缓存不改；只有会改动原生搜索结果的名称兜底受此次门禁约束。共享队列仍保持原有串行规则，不新增另一条并行 Native 通道。
- 用户主动点击拍卖助手搜索仍走显式查询路径。跑商中双击货物虽然属于用户发起的询价，也不能获得抢占原生窗口的权限。

### 1.3 可见性由服务提供即时、有限读取

新增 `AuctionSurfaceV3:ReadVisibility()`，只在搜索准入、在途回包及既有活跃报价调度中读取：优先使用原生第五返回值的布尔可见性；兼容四返回值时读取有限的内容对象父链。父链排除始终可见的 `UIParent`，非布尔值不冒充“已关闭”。可确认的有效几何只可作为可见证据，不作为已关闭证据。

该方法不启动拍卖助手、不开窗口、不发布观察事件、不更新几何快照。Query 与 Queue 在 TOC 中先于 Surface 加载，因此查询依赖在调用时解析，避免捕获加载期 nil。

### 1.4 在途请求让出结果所有权，而不是伪造取消

当前包内使用的 `AUCTION_ITEM_SEARCHED` 没有逐请求令牌，本次没有引入未经核实的原生取消 API。

当后台名称查询已发出、随后发现玩家打开拍卖行时：将其标记为 interrupted，丢弃其结果读取资格；保留至该请求原有 8 秒超时点的占位。隔离期间不调用 `GetSearchedItemCount/Info` 来读取玩家结果，也不会因为收到一次玩家的搜索回包就提前宣布旧请求已排空。

定时回调和事件回调绑定当前请求对象，旧回调不能误结束替换后的请求。超时任务在发送 Native 前注册，注册失败不发送；同步返回也能正确移除任务。

**限制：已经发送给服务器的查询不能由本补丁撤回。打开拍卖行的瞬间仍可能遇到那一个在途请求带来的原生结果刷新；本次阻止的是后续反复搜索，并按上述有限隔离策略拒绝失去归属的结果。8 秒是现有超时策略，不是服务器保证的最大网络延迟；没有请求令牌就不能宣称能绝对识别任意迟到的原生事件。**

### 1.5 暂停不是失败，保留用户任务和价格

暂停保留当前材料、剩余队列、请求身份和消费者；不增加完成数，不记作空结果，不写负缓存，不清除已确认材料价格。暂停时长不计入名称搜索原有 12 秒准入期限，长时间使用拍卖行后仍能继续同一未取消任务。

最后一个需求取消时释放报价调度，不会关窗后重启已取消的查询；多个货物共享材料时，只取消其中一个不会误杀其余需求。已经发出的旧 Native 占位只保留原有有限超时。

### 1.6 状态展示和诊断

新增独立活动事件 `v3.price_quote.activity` 及只读 `quoteActivity` 投影，通知已有跑商消费者更新文案，不使用会触发材料终态对账的 `v3.price_quote.completed`。

主页面、悬浮窗及首页共用展示会显示：

> 拍卖行使用中，材料名称查询已暂停；关闭拍卖行后自动继续

未知可见性、等待手动查询、隔离旧回包有各自原因。已有来源错误仍优先显示。未改控件位置、尺寸、拖动恢复或配置。

跑商模块诊断的 `queue.activity` 和 `auctionOwnership` 可看到暂停原因、可见性证据来源、失去归属状态、隔离截止时间与丢弃计数。诊断读取不触发原生探测或搜索。补丁标识为 `auction-user-priority-1`，BuildTag 没有更改。

## 3. 性能影响

没有增加常驻 Tick、第二条报价轮询或永久拍卖观察任务。仅利用仍有需求时的原有 1 秒报价调度，增加少量可见性读取；父链最多检查 9 层并排除 UIParent。发包前和回包时另有固定次数的边界校验。

暂停时不发送名称搜索，也不读取拍卖结果列表。内存新增少量活动字段和一个在途请求的隔离标记；活动只在状态/原因改变时发布，稳定暂停不会每秒重绘。最后一个需求释放后移除队列任务，旧在途请求的定时器到原超时点回收。

没有客户端 CPU/FPS 实测，不能给出百分比提升或帧率收益。

## 4. 兼容风险与安装

退出游戏并备份后，将补丁内 `replicatedsuite/` 合并覆盖到现有 Addon 下的同名目录。不要先删除旧目录，不要清空存档。基线应已包含本轮此前三份增量补丁；本包不重复交付它们。

本次不迁移用户配置、不删除价格缓存、不改收藏和追踪，也不改窗口坐标。首次覆盖完整重启客户端，再验证热重载。

兼容风险：旧客户端无法可靠证明窗口已关闭时，名称兜底会显示等待，而不是猜测后继续抢占；请保留诊断里的可见性来源。用户主动从拍卖助手发起搜索，如果恰好还有旧无令牌请求隔离，会返回既有忙提示；直接操作原生拍卖行不经过本门禁。

### 必测用户场景

1. 连续给两个货物加入询价，在材料查询中打开原生拍卖行。手动输入另一物品、搜索、翻页并停留至少 30 秒，确认不会继续被后续材料抢走结果。
2. 关闭拍卖行，确认未取消货物按节流继续，已取得的价格仍在，材料/货物完成数没有因暂停重复增加；停留两分钟后再关闭也应能恢复。
3. 先关闭插件拍卖助手，再重复第 1 项，确认保护不依赖侧栏开启。
4. 等待期间取消任务或关闭跑商功能，随后关闭拍卖行，确认已取消查询不再恢复；仅取消一个共享材料货物时，其余任务仍保留。
5. 检查用户主动点击拍卖助手收藏搜索仍能使用；旧查询隔离期内允许有短暂忙提示，不允许自动连续改写用户搜索。
6. 覆盖后完整重启与热重载分别测试，保留跑商模块诊断中的 `queue.activity` 和 `auctionOwnership`。若仍反复跳转，记录打开拍卖行的时刻、是否开启拍卖助手、是否已关闭其他可能搜索拍卖行的插件，并提供完整模块诊断，不要先清缓存或存档。
